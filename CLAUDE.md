# CLAUDE.md — hono-mongo-test-api

Seconde API de test des boilerplates front, interchangeable avec `../api-platform-test-api` (8090). Les conventions générales sont dans `~/.claude/CLAUDE.md` : ce fichier ne note que les choix propres au projet.

## Règle d'or

**Le contrat est celui de l'API Platform**, pas celui qu'on trouverait plus propre. Toute modification d'une réponse se vérifie par `make contract` (les deux API lancées). Un écart assumé se déclare dans `contract/cases.ts` (`knownDifference`) et dans le tableau « Écarts connus » du README.

## Choix du projet

- **Architecture** : un seul contexte, quatre modules (`task`, `blog`, `contact`, `catalog`), comme l'API Platform. `domain/` = types en namespaces, constantes, port du dépôt, règles pures, sans aucune dépendance. `application/` n'existe que dans le catalogue (D9) : `searchProducts` charge l'arbre, résout la catégorie (404) et délègue au dépôt, la route ne fait plus que traduire. Blog, contact et tâches restent des transaction scripts sans couche application (Khononov p. 124). `infrastructure/` = schéma zod du document, adaptateur, fixtures. `http/` = contrat publié, routes `createRoute` et adaptation HTTP. `app.ts`, `database.ts` et `server.ts` composent (seuls fichiers autorisés à importer tous les modules), `shared/` porte le transverse technique et n'importe aucun module.
- **Le domaine n'est pas le contrat** (décision D10 de `boilerplates-commun/ARCHITECTURE-DDD.md`, Evans p. 264) : cette API est conformiste au langage publié de l'API Platform. Tout ce qui fige la parité (schémas OpenAPI avec `.meta({ id })`, messages exacts, codes Symfony, `phpTrim`, sémantique de requête PHP) vit dans `http/` (`contract.ts` par module, `productQuery.ts`, `deserializeContactMessage.ts`). Le domaine garde des types, des constantes et des règles qui renvoient des violations neutres. Le compilateur vérifie à chaque route que le type du domaine est assignable au type du contrat. Le document MongoDB a son propre schéma zod, traduit en `$jsonSchema` par `toBsonSchema`.
- **Node exécute les `.ts`** (type stripping natif de Node 24) : pas d'étape de build, l'image de prod copie `src/`. D'où `erasableSyntaxOnly` (ni `enum`, ni propriétés de paramètre, namespaces de types en `declare namespace`), les imports en `.ts` et l'alias `#/` par le champ `imports` de `package.json` (résolu par Node, TypeScript et Vite sans configuration).
- **Identifiants entiers** : `_id` numérique (fixtures), compteur atomique `counters` pour les messages de contact, comme la séquence PostgreSQL. Catégories : `_id` = slug.
- **Value objects du catalogue** (D8, même vocabulaire que l'API Platform) : en données immuables et fonctions pures, sans classe. `Price` est un type marqué (`number & { [PRICE]: true }`) que seul `Price.fromCents` produit, après vérification (entier positif ou nul, centimes) : le compilateur refuse un nombre brut là où un prix est attendu, et refuse aussi d'assigner un nombre du contrat à un `Price` du domaine. `Price` ne porte pas `compareTo` ni `isBetween` comme en PHP : ici le filtre et le tri par prix sont faits par MongoDB, ces fonctions seraient du code mort. `CategoryTree` (`of`, `find`, `childrenOf`, `pathTo`, `toNodes`) remplace les fonctions éparses de parcours d'arbre.
- **Pagination** : `page` bornée à 1 000 000 (`MAX_PAGE`), comme l'API Platform, pour garder le décalage dans les entiers sûrs.
- **Catalogue** : `categoryPath` (slugs de la racine à la feuille) dénormalisé sur chaque produit. Filtre de branche = `{ categoryPath: slug }` sur un index multiclé, compteur de sous-catégorie = `$unwind` + `$group` sur ce même champ. Une agrégation `$facet` calcule page, total et compteurs disjonctifs. Tri stable par `_id` en second critère (le `usort` de PHP 8 est stable), collation `fr` seulement pour le tri par nom, pour garder les index des autres requêtes.
- **Paramètres du catalogue** : lus par `parsePhpQuery` avec la sémantique PHP (dernière affectation gagnante, `a[]`, `a[k]`, `%5B` en toute casse), puis `parseCriteria` (domaine) ignore toute valeur invalide. Le schéma `request.query` de la route est documentaire (`z.unknown().meta({ type })`) : un validateur zod rejetterait ce que l'API Platform ignore.
- **Formulaire de contact** : `bodyLimit` à 64 Ko (413 problem+json en français, écart assumé : l'API Platform lit tout le corps), `requireJsonContentType` (415), `negotiateFormat` (406), `scenario`, puis `deserializeContactMessage` reproduit le serializer Symfony (500 « Syntax error », identifiant fourni, type invalide dans l'ordre du corps). Les règles (champs obligatoires, longueurs en points de code, 255 pour le nom et l'e-mail, 5000 pour le message, e-mail HTML5) sont dans `contactMessageViolations` (domaine, violations neutres). `http/contract.ts` mesure le nom et le message après `trim` PHP, traduit chaque violation en contrainte Symfony (NotNull, NotBlank, Length, Email : code et message exacts) et les branche sur le schéma par `superRefine`.
- **Erreurs** : classes dédiées (`CategoryNotFoundError`, `ContactMessageValidationError`, `NotAcceptableError`…), traduites en `application/problem+json` dans `app.onError`. Le corps prend la forme JSON-LD d'API Platform (`@context`, `@id`, `@type`, `description`) sauf si le client demande explicitement `application/json` ou n'envoie pas d'Accept (`errorFlavor`). Routes inconnues : JSON du routeur Symfony, 405 avec `Allow`.
- **Suivi des erreurs (GlitchTip)** : `src/shared/infrastructure/errorReporting.ts`, branché par `app.onError` (le rapport part après la même décision `isExpected` que le journal, la réponse problem+json ne change pas) et par `server.ts`. Écartées : toutes les 4xx, dont la 422 de validation, et les 500 simulées par `X-Scenario`. Les 404 et 405 du routeur ne passent pas par `onError`. Une 500 de désérialisation (JSON invalide) n'est pas envoyée : c'est une erreur du client, la 500 ne sert que la parité avec l'API Platform. Sentry 11 n'a plus `sendDefaultPii` : `dataCollection` coupe utilisateur, cookies, en-têtes, corps et paramètres d'URL, et `beforeSend` retire encore `request.data` et `request.cookies`. Le test garde le vrai transport du SDK (`createTransport`) et remplace seulement l'envoi réseau, sur un DSN factice.
- **CORS** : réécrit à la main (`shared/http/cors.ts`) pour reproduire nelmio/cors-bundle, dont le préflight diffère du middleware `cors` de Hono (200 et non 204, en-têtes renvoyés à une origine refusée, 400 « Unauthorized header »). Regex insensible à la casse dans `CORS_ALLOW_ORIGIN`.
- **CSP** : `Content-Security-Policy: default-src 'none'; frame-ancestors 'none'` sur toutes les réponses sauf le HTML (`shared/http/contentSecurityPolicy.ts`), même en-tête que l'API Platform. Une API JSON ne charge rien et ne s'affiche pas en iframe ; la Swagger UI de `/api/docs` charge ses scripts et en est exclue. CSP bloquante et sans `report-uri` : il n'y a pas de page dont collecter les violations.
- **X-Scenario** : middleware par route, désactivé quand `APP_ENV=prod`. Ordre identique à l'API Platform : 415, 406, puis scénario, puis lecture du corps.
- **Tests d'intégration** : `app.request` contre un MongoDB réel (celui de Compose, ou le service de la CI), une base par fichier (`app_test_<nom>`) pour que les fichiers tournent en parallèle. Pas de mongodb-memory-server : il télécharge un binaire `mongod` à l'installation, d'une version qui ne serait pas celle de l'image, et le service Compose existe déjà.
- **Docker** : MongoDB non publié sur l'hôte, API sur `127.0.0.1:8091`. Seuls prérequis : Docker avec Compose, `make` et git (SPEC-COMMUNE, section 18). Les commandes de qualité passent par `docker compose exec -T api`, en local comme en CI. `make install` et `make lint-staged` utilisent un conteneur ponctuel (`run --rm --no-deps api`), pile lancée ou non. `make contract` passe par le service `contract` (profil `tools`, `network_mode: host`) pour joindre 8090 et 8091 depuis le conteneur. L'image de dev ajoute `git` à `node:24.14-alpine` pour Husky et lint-staged.

## Dépendances ajoutées, et pourquoi

- `@hono/swagger-ui` : Swagger UI sur `/api/docs` (navigateur), comme l'API Platform. Sans Accept HTML, `/api/docs` sert le JSON OpenAPI.
- `vite` (dev) : dépendance pair de Vitest 5.
- `@sentry/node` 11.6 : suivi des erreurs dans GlitchTip, imposé par la section 16 de SPEC-COMMUNE. Poids mesuré à l'installation : 27 paquets ajoutés, environ 85 Mo sur disque, surtout les instrumentations OpenTelemetry dont dépend le SDK (`@sentry/core` 8,5 Mo, `@sentry/node` 2,8 Mo). Aucun effet de bundle (serveur), effet sur l'image de production non mesuré. Le SDK n'est initialisé que si `GLITCHTIP_DSN` est renseigné, avec les seules intégrations utiles (exceptions et rejets non gérés, erreurs liées, dédoublonnage) : pas d'instrumentation HTTP, pas de trace.
- `globals`, `@eslint/js`, `typescript-eslint` (dev) : configuration ESLint plate.

## Règles d'architecture (D6, R13)

- **Outil** : `no-restricted-imports` d'ESLint, configuré dans `eslint.architecture.mjs`, comme le recommande D6 pour ce dépôt. Chaque couche de chaque module reçoit une liste blanche d'imports internes (`#/<module>/<couche>/`) écrite en expression régulière, plus l'interdiction des paquets hors couche (zod, Hono, MongoDB). Le défaut connu de cette règle, le contournement par un chemin relatif, est fermé par l'interdiction de `../` partout : un import interne passe toujours par `#/`, `./` reste dans le même dossier donc la même couche.
- **Pourquoi pas `eslint-plugin-boundaries`** : il raisonne sur le chemin résolu et non sur la chaîne d'import, mais il lui faut un résolveur qui comprenne le champ `imports` de `package.json` (`#/`), ce que les résolveurs d'eslint-plugin-import ne garantissent pas sans essai. Avec `../` interdit, `no-restricted-imports` couvre les mêmes cas sans dépendance ajoutée, et l'auto-test le prouve.
- **Auto-test** : `make arch-selftest` (dans `make qa`, donc en CI) écrit six violations volontaires à leur emplacement réel (domaine vers infrastructure, domaine vers `http/` par `../`, domaine vers Hono, `http/` vers infrastructure, un module vers un autre, `shared/` vers un module), exige pour chacune l'échec d'ESLint avec le message de la règle, puis retire le fichier. Une règle débranchée fait échouer la QA.
- Les motifs utilisent `regex` et non `group` : `group` suit la syntaxe gitignore, où `#` en début de motif est un commentaire.

## Règles de lint ajustées

- `@typescript-eslint/no-unused-vars` avec `ignoreRestSiblings: true` : retirer un champ d'un document par déstructuration (`{ _id, categoryPath, ...product }`) est l'écriture la plus lisible, la variable écartée est voulue.
- `@typescript-eslint/consistent-type-assertions` en `never` : aucun `as` (hors `as const`), le narrowing passe par des gardes ou par zod. Une seule exception, désactivée sur sa ligne et commentée : la création du type marqué dans `Price.fromCents`, car une marque de compilation ne peut naître que d'une assertion.
- `@typescript-eslint/no-namespace` avec `allowDeclarations` : namespaces de types uniquement (`declare namespace`).
- `no-console` autorise `info`, `warn`, `error` : journal de démarrage et scripts.

## Pièges rencontrés

- **`mongo:8` ne démarre pas** sur ce noyau (7.0) : message « Linux kernel versions 6.19 and newer has a known incompatibility ». Image épinglée en `mongo:8.2`, y compris en CI.
- **`$jsonSchema` n'est pas du JSON Schema** : MongoDB refuse `type: "integer"`, `$schema`, `format`, `default`. `toBsonSchema` réécrit tout en `bsonType` (`int`/`long` pour les entiers, `date` pour `z.date()` via `override`) et retire les bornes d'entier sûr que zod ajoute.
- **`.meta({ id })` et `z.toJSONSchema`** : un sous-schéma nommé produirait `$defs`/`$ref`, refusés par MongoDB. Les schémas de document ne réutilisent donc aucun schéma nommé (les énumérations sont des `z.enum(EXPOSURES)` locaux).
- **zod-openapi ne sait pas documenter `.catch()`** (`UnknownZodTypeError`) : d'où `z.unknown().meta({ type })` pour les paramètres du catalogue.
- **Hook de validation** : en échec, le résultat n'expose pas `data` dans ses types. Les violations sont relues depuis les issues zod (`violationsFromIssues`, code Symfony dans `params.code`).
- **Tableau JSON sur le contact** : PHP le désérialise comme un objet sans champ, donc 422 sur les trois champs. zod rejette un tableau à la racine, le hook le ramène à `{}`.
- **Symfony normalise la query string** avant API Platform : `exposure%5b%5d` (minuscules) filtre comme `exposure[]`. Trouvé par le test de contrat.
- **Forme des erreurs selon Accept** : `*/*`, `application/*`, un type inconnu ou `application/json; charset=utf-8` donnent la forme JSON-LD. Seuls `application/json` explicite et l'absence d'Accept donnent la forme simple. Le Content-Type reste `application/problem+json`.
- **415 avant 406** sur le `POST`, et `X-Scenario: error` avant la lecture du corps (un JSON invalide reçoit la 500 simulée).
- **`fetch` ajoute `Accept: */*`** : le script de contrat passe par `node:http` pour maîtriser chaque en-tête (l'absence d'Accept change la forme des erreurs).
- **`curl` et les crochets** : sans `-g`, curl interprète `[...]` comme un motif. Toujours `curl -g` pour tester les paramètres du catalogue.
- **Husky dans le conteneur** : `node:24.14-alpine` n'a pas `git`, et `husky` (script `prepare`, lancé par `yarn install`) échoue sans lui. L'étape `dev` du Dockerfile installe `git`. `prepare` reste `husky || true` pour l'image de production, installée avec `--ignore-scripts`.
- **`c.json(body, status, { 'Content-Type': … })`** garde le Content-Type fourni : c'est ainsi que les erreurs sortent en `application/problem+json`.
